このサイト「さいはてラボ」は、AIのClaude（Claude Code）と一緒に作りました。サイトを組み立てるプログラムも、記事の書き方のルールも、毎日の更新の流れも、AIとやりとりしながら形にしています。

結論から書くと、立ち上げの中身は次の3つです。

- **サイトの本体**：Markdownで書いた記事を、Pythonの小さなプログラムでWebページに変換する
- **公開の仕組み**：GitHubに置いた原稿を、Netlifyが自動でビルドして公開する
- **運営マニュアル**：AIが毎日記事の下書きを作るときに従うルールを、1つのファイルにまとめる

この記事では、それぞれを実際のファイルの中身を見ながら紹介します。

## サイトの本体は「Markdown＋小さなPythonプログラム」

WordPressのようなブログサービスは使っていません。記事は1本ずつ、Markdownという書式のテキストファイルです。ファイル名は「日付-英語のスラッグ.md」と決めていて、たとえばこの記事は `2026-10-29-building-saihate-lab-with-ai.md` です。

ファイルの先頭には、タイトルや説明文、カテゴリなどの情報をまとめて書きます。

```yaml
title: 記事タイトル
description: 検索結果に出る説明文
date: 2026-10-29
category: ai        # ai（AI実践記）または local（道東ローカル）
status: draft       # draft（下書き）→ OKが出たら published
pr: false           # 広告リンクを含むなら true
```

これを `build.py` というPythonのプログラムが読み込み、記事ページ、トップページ、カテゴリごとの一覧、RSS、サイトマップをまとめて書き出します。使っているライブラリは、Markdownを変換するものと、先頭の情報を読むものの2つだけです。

ポイントは `status` と `pr` の2つの項目です。

- `status` が `published` の記事だけが本番に出ます。`draft` のままなら、ファイルがあっても公開されません
- `pr` を `true` にすると、記事の一覧と本文の上に「PR」の表示が自動で付きます

広告を含む記事に「PR」を付け忘れないよう、人の注意力ではなく仕組みのほうで表示するようにしました。2023年10月から、広告であることを隠した宣伝（いわゆるステマ）は景品表示法の規制対象になっています。小さな個人メディアでも、ここは最初から決めておきたかったところです。

## 公開は「GitHubに置けばNetlifyが自動で」

原稿とプログラムは、GitHubのリポジトリ（ファイルの置き場所）で管理しています。そこにNetlifyというホスティングサービスをつなぎ、`main` という本番用の枝（ブランチ）が更新されると、自動でビルドして公開されるようにしました。

Netlify側の設定は、`netlify.toml` というファイルに数行書いただけです。

```toml
[build]
  command = "pip install -r requirements.txt && python3 build.py"
  publish = "dist"
```

もう1つ便利なのが、本番以外のブランチにも、ブランチごとの確認用ページ（プレビュー）を作ってくれる機能です。たとえば `draft-20261029` というブランチを作ると、`https://draft-20261029--saihate-lab.netlify.app/` のようなURLで、そのブランチの中身だけを確認できます。本番には一切影響しません。

## 「AIが書いて、人が確認して、公開する」流れ

次に、記事を公開するまでの流れです。

1. AIが、届いた素材（写真やメモ）かネタ帳から1本選んで下書きを書く
2. 下書きを `draft-日付` という名前のブランチに置く
3. Netlifyが作ったプレビューのURLを、運営者に知らせる
4. 運営者が読んで、OKなら本番に反映する。直してほしい点があれば同じブランチで直す

最後の「運営者の確認なしに本番へ反映しない」は、マニュアルの中でも太字にして念を押しています。返事がない日は下書きのブランチを残したままにし、未確認の下書きが3本たまったら、新しい下書きは作らずに確認をうながす、というところまで決めました。

実は、この流れは立ち上げた日のうちに一度変えています。最初は「プルリクエスト」というGitHubの仕組みを使って確認する形にしていましたが、その日のうちに、今の「draft-ブランチのプレビューを見て確認する」形に書き換えました。ルールが1つのテキストファイルにまとまっているので、流れを変えるときも、そのファイルを書き換えるだけで済みます。

## AIに渡した運営マニュアルの中身

AIが毎日の作業で読むのが、`CLAUDE.md` という運営マニュアルです。サイトの構成、記事の書き方、公開の流れが、すべてここに書いてあります。

中でも大事にしているのが「書き方のルール」です。一部をそのまま紹介します。

- 一次情報が命：運営者の体験・写真・メモに書かれていないことを、体験したように書かない。架空の店名、数字、エピソード、感想を作らない
- 事実（営業時間、料金、イベントの日程、ツールの仕様など）は、Web検索で公式の情報を確認してから書き、確認できないものは書かない
- 用語の説明だけ、情報のまとめだけの記事は作らない。必ず「実際にやってみた」「現地で見た」の要素を入れる

AIは、頼めばそれらしい体験談をいくらでも書けてしまいます。だからこそ、このマニュアルでは「書いてはいけないこと」を先に決めています。道東のお店やイベントの情報が、実在しない内容だったら意味がありません。

広告についても、「実際に使ったもの、運営者が勧めると言ったものだけを紹介する」「リンクは運営者が用意したものだけを使う」と決めています。

## この記事も、その流れで作られています

じつは、いま読んでいるこの記事も、ここで紹介した流れで作られました。AIがネタ帳から「AIでメディアサイトを立ち上げた全工程」を選び、リポジトリの中身を確かめながら下書きを書き、プレビューを運営者に送って、確認を受けてから公開しています。

ネタ帳には、Claude Codeで作った歴史アドベンチャーゲームや、縦型のPR動画づくりなど、これから書きたい実践の話が並んでいます。仕組みができたので、ここからは中身で勝負です。道東の現場で手を動かした記録を、少しずつ積み上げていきます。
